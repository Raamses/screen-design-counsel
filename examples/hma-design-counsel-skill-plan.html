The Skill: Screen-Design-Counsel PILOT-FIRST

Full spec — from complaint to implementation. Every "this screen is broken / crowded / confusing" enters one fixed process.

The process (6 steps)

  1. Anatomy extraction — screenshot + reading the real component (DOM + CSS) → precise defects (crowding, overlap, bidi, touch-target sizes)
  2. Design directions — 3-4 concrete alternatives
  3. Live mockup gallery — one HTML page on the Pi share server (:8909), phone-first: live mock + toggles + pick copying
  4. Ram reads picks in Telegram — the copied pick IS the spec
  5. Gated implementation — builder (glm/agy) + review ladder (agy binding → Claude at quota reset) in an isolated worktree
  6. 390×844 screenshot verification — playwright + compare to the mockup before merge
Complaint→Anatomy→Ideation→Pick gallery→Spec→Gated build

Canvas feel: Figma-like, simplified

Selection and controls mimic Figma, stripped to the minimum: objects with bounding-box outlines, tap = select, hold ~1s = select the PARENT element (the tag relocates up a level — hold again to climb further), tap-again = untag, chip-tap = edit the note, long-press = untag-all (multi-select via plain taps), and an inspector-lite for the selected element. Drag stays out of V1 — it arrives with V2 if the pilot shows the need; the taps stay the primary gesture. Capability reminder: a first-run gesture legend (dismissed by the first tap), a persistent "?" chip for recall, and an idle nudge that fades out after your first tag — non-blocking, state-aware.

Ram's ruling 22:42: "Make it something like a figma screen, it can be simplified but the selecting and controlling can be similar."

Special tooling (V1)

• template.html — one 390×844 phone-frame with CSS-var token slots (--c-bg, --c-card, --c-accent, --c-text…); different layouts come from the candidates' content blocks, not from template variety

• extract_tokens.py — pulls the repo's palette tokens (tailwind config / theme CSS) into the template's CSS variables — re-run every pass, never hardcode (anti-drift)

• gen_candidates.py — writes N numbered candidate pages into passes/<repo>-<screen>-<date>/ from the template

• verify.py — Playwright 390×844 (he primary, en secondary): PNG per page + a headless bounding-box overlap report; the SAME check re-runs on every implementation PR before review

Pick capture = localStorage + copy-back (the Copy picks button). Not in V1: a /picks POST endpoint on the share server, multi-screen galleries, A/B diffing, dashboards, per-repo SKILL.md variants.

Invocation contract

/counsel screen <component-path> "<complaint>"

Natural triggers: "this screen is broken / crowded / confusing on mobile". Required inputs: the component path, the screen URL/path, the complaint. Skip heuristic: styling-only (colors/padding) → direct fix, no counsel; structural (DOM layout / bidi mixing / crowding) → full counsel (agy + Hermes + AmosBot).

Hermes (Claude): PILOT-FIRST — "ship a pilot, not a platform" — plus one tooling correction and a strict tier ladder:

• No POST server in V1 — a static gallery can't push anything; picks stay in localStorage + a copy-back summary block (exactly like the live ideas page). The mockup-server.py POST endpoint is dropped.

• Tier ladder: T0 = mechanical violations caught by tooling (overlap check, locale-parity, contrast tokens) → direct fix, no counsel · T1 = one-decision fixes after a failing T0 · T2 = full gallery counsel ONLY for multi-direction layout systems, RTL/bidi or kid-cognition risk, or Ram-flagged screens. A screen enters T2 at most once; regressions re-enter via T0/T1 with the gallery diffed against the prior pass.

• Invocation gate: the skill fires ONLY when (1) a screenshot + the component path exist, and (2) the complaint is visual/layout (crowding, overlap, bidi-mix, contrast) — not behavior/logic.

• Per-pass artifacts: passes/<repo>-<screen>-<date>/ holds the numbered candidate pages + verdict.json; palette tokens are re-extracted from the repo's theme on EVERY pass (anti-drift). Canonical truth stays in the repo (tests) + mailbox (decisions) — no parallel memory.

• One ruler for mockups and code: no candidate reaches Ram's gallery and no implementation PR merges until it passes the same 390×844 headless overlap check + PNG harness (reuse the e2e viewport patterns — e2e/arcade-game-over.spec.ts already does bounding-rect-in-viewport checks).
